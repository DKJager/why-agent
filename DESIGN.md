# DESIGN.md — Why-Agent

**Open Agent Hackathon 2026 · Track 02 "The Agent That Can Explain Why"**
An agent that investigates a business question across several data sources, connects the findings, and returns an evidence-backed answer with a visible reasoning trace.

> **All data in this repository is fictional.** "Northwind-Lite", every customer, order, carrier (NordExpress, RheinFracht, …) and ticket is synthetic and generated by `data/generate_sample_data.py`. No real company, person or carrier is represented.

## 1. Goals and non-goals

**Goals**
1. Answer "Why did EU revenue drop in week 41?" by actually querying three sources (orders, support tickets, shipments), joining them, and ranking causes with numbers.
2. Every claim in the final answer is backed by a cited evidence item (aggregate and/or row ids) that a Critic has re-verified.
3. Trace of every step (JSONL file and stdout).
4. H-MEM: confirmed findings are stored per entity and recalled in a later session, behind an `EngineAdapter`, with a fully working offline stub.
5. Runs fully offline with `SAMPLE_MODE=true`, using real logic. The answer changes when the data changes.
6. Bounded runs and structured errors.

**Non-goals:** UI, auth on the HTTP endpoint, multi-tenant memory, streaming, any dependency beyond Python 3.12 stdlib + `requests`.

---

## 2. Principle: the model never produces numbers

The LLM (Nemotron in live mode) only helps with language: parsing the question, wording sub-questions, writing narrative. **All numbers come from code** that queries the sources. A claim is accepted only if the Critic can re-derive its numbers from cited evidence. A narrative is accepted only if every number in it maps to an accepted claim. If the model misbehaves, the pipeline falls back to the deterministic renderer in `agent/rules.py`, which is also what `SampleProvider` uses. This gives the guarantee that an uncited claim never reaches the answer, regardless of model quality.

### 5.2 Planted cause and decoys (generator contract)

| Element | Specification |
|---|---|
| **Planted cause** | A fictional **NordExpress** hub outage (Rotterdam hub) from 2026-10-01 to 2026-10-10. NordExpress carries ≈45% of EU orders. EU shipments with `carrier=NordExpress` and `ship_date` in that window get `delay_days` in 4–9 (otherwise 0–1). |
| Effect on orders | NordExpress EU orders placed in week 41: 55–65% end `cancelled` with `cancel_reason=delivery_delay`. In week 40, Oct 1–4 only, about 10–15%. Other carriers keep a baseline cancel rate of about 3%. |
| Effect on tickets | EU `delivery_delay` + `where_is_my_order` tickets rise from about 8/week to about 45 in week 41, with `order_id` pointing at NordExpress orders. |
| **Demand unchanged** | EU *gross* order value in week 41 is within ±8% of the weeks 37–40 mean. The drop is fulfilment, not demand. |
| Decoy 1 | EU `home` category is about −4% organic noise in week 41. |
| Decoy 2 | UK `payment_issue` tickets bump by +3 in week 41 (noise). |
| Control | US and UK net revenue in week 41 are within ±6% of the baseline. |

**Invariants a test may rely on** (verified independently by recomputing from the CSVs with the `csv` module, never from hardcoded constants): EU net revenue week 41 is ≥20% below week 40; ≥60% of the EU week-41 vs week-40 delta equals cancelled value with `carrier=NordExpress` and `cancel_reason=delivery_delay`.

## 6. Sources (`agent/sources.py`)

The agents never write SQL or touch CSVs directly. They build a **`QuerySpec`**. `CsvSource` executes it in Python and `ZetarisSource` compiles it to SQL, so the agent logic is identical in both modes.

### 6.1 Interfaces

```python
Op = Literal["=", "!=", ">=", "<=", "in", "is_null", "not_null"]

@dataclass(frozen=True)
class Filter: column: str; op: Op; value: Any = None
@dataclass(frozen=True)
class Agg:
    fn: Literal["sum", "count", "avg", "min", "max", "count_distinct"]
    column: str | None; alias: str
@dataclass(frozen=True)
class QuerySpec:
    table: Literal["orders", "tickets", "shipments"]
    filters: tuple[Filter, ...] = ()
    select: tuple[str, ...] = ()
    group_by: tuple[str, ...] = ()
    aggs: tuple[Agg, ...] = ()
    order_by: tuple[tuple[str, Literal["asc", "desc"]], ...] = ()
    limit: int = 1000
    def as_dict(self) -> dict: ...
    @staticmethod
    def from_dict(d: dict) -> "QuerySpec": ...

@dataclass
class QueryResult:
    rows: list[dict]; row_count: int; query_text: str
    source: str            # "csv" | "zetaris"
    elapsed_ms: int; truncated: bool

class DataSource(Protocol):
    name: str
    def describe(self) -> dict[str, list[str]]: ...         # table → columns
    def query(self, spec: QuerySpec, *, timeout_s: float | None = None) -> QueryResult: ...
    def health(self) -> dict: ...                           # {"state": "online"|"offline"|"unauthorized", "detail": str}
    def fingerprint(self) -> str: ...                       # sha256 of data (CSV) or "live"
```

Validation (both implementations): unknown table or column → `SourceQueryError`; `limit` is clamped to ≤5000.

### 6.2 `CsvSource(data_dir: str)`
Loads the three CSVs with `csv.DictReader` and casts types using the §5.1 schema. It performs no network I/O. `query_text` looks like `csv:orders where iso_week=41 and region='EU' group_by(category) sum(order_value_eur)`. `fingerprint()` is the sha256 of the concatenated file bytes. Reloading is by file mtime, so tests that mutate a copied `DATA_DIR` see fresh data.

### 6.3 `ZetarisSource(base_url, api_key, tables, timeout_s)`
- `POST {base_url}/sql-editor/sqls/run` with header `Authorization: Bearer <api_key>` and `Content-Type: application/json`.
- SQL is compiled from `QuerySpec` with an identifier whitelist (columns of the known schema only) and literal escaping (single quotes doubled, numbers validated). No free-form SQL ever comes from the model.
- **A1 (assumption):** `_build_request(sql) -> dict` produces the body (provisionally `{"sql": sql}`), and `_parse_response(obj) -> list[dict]` tolerantly accepts `{"rows":[{…}]}`, `{"data":[{…}]}`, or `{"columns":[…],"data":[[…]]}`. Both are the only places to change once the setup guide's exact shapes are confirmed.
- Retries: 2 retries (backoff 0.5 s, 1.5 s) on connection errors, timeouts and 5xx. 4xx is not retried. 401/403 → `SourceUnauthorized`.
- The key is never logged, and `query_text` is the SQL only.

### 7.2 URL helpers (contract: Meterless Runtime 1.4, provider contract v4)

```python
DEFAULT_BASE_URL = "http://127.0.0.1:8088/v1"
PLACEHOLDER_TOKENS = {"", "rt-local", "your-key-here", "changeme"}

def normalize_base_url(raw: str | None) -> str: ...
def parse_connect_link(raw: str) -> tuple[str, str | None]: ...   # (base_url, key); NEVER log the input or the key
def healthz_url(base_url: str) -> str: ...                        # base minus trailing "/v1", plus "/healthz"
def validate_token(token: str | None) -> str: ...                 # raises ProviderUnauthorized("placeholder") on §PLACEHOLDER_TOKENS
```

`normalize_base_url` rules:
1. Empty or `None` → `DEFAULT_BASE_URL`.
2. No scheme → prefix `http://`.
3. Drop query and fragment, then trailing `/`.
4. Repeatedly strip a trailing segment from `{/healthz, /v1/models, /v1/chat/completions, /v1}` until none matches (so `/v1/v1` also collapses).
5. Append `/v1`. The result **never** ends in `/v1/v1`, and any other path prefix (e.g. `/gw`) is preserved.
6. IPv6 literals like `[::1]:8088` are preserved.

| Input | Output |
|---|---|
| `127.0.0.1:8088` | `http://127.0.0.1:8088/v1` |
| `http://127.0.0.1:8088` | `http://127.0.0.1:8088/v1` |
| `http://127.0.0.1:8088/v1` | `http://127.0.0.1:8088/v1` |
| `http://127.0.0.1:8088/v1/` | `http://127.0.0.1:8088/v1` |
| `http://host:8088/v1/chat/completions` | `http://host:8088/v1` |
| `http://host:8088/v1/models` | `http://host:8088/v1` |
| `http://host:8088/healthz` | `http://host:8088/v1` |
| `localhost:8090/v1/v1` | `http://localhost:8090/v1` |
| `[::1]:8787` | `http://[::1]:8787/v1` |
| `https://gw.example.com/meterless/v1/models` | `https://gw.example.com/meterless/v1` |
| `""` / `None` | `http://127.0.0.1:8088/v1` |

`parse_connect_link("http://10.0.0.5:8088/connect#k=SECRET")` → `("http://10.0.0.5:8088/v1", "SECRET")`. A string that is not a connect link returns `(normalize_base_url(raw), None)`.

### 7.3 `MeterlessProvider(base_url, token, app_id="why-agent", model_id="meterless/auto", timeout_s=180)`
- Every request carries `Authorization: Bearer <token>` and `meterless-app: why-agent`. Chat requests additionally carry `meterless-scope: user`.
- `chat` → `POST {base}/chat/completions`, body `{"model": model_id, "messages": [...], "temperature", "max_tokens"}`. Plain-text messages keep `content` as a **string** (never a parts array). `json_mode=True` adds `response_format={"type":"json_object"}`. If the runtime rejects it with 400, retry once without it and validate JSON ourselves.
- `list_models` → `GET {base}/models`. Keep every id starting with `meterless/`, **including unknown ones**. Known ids: `meterless/{auto,fast,deep,cheap,local,fusion}`, `meterless/<class>`, `meterless/<class>.<disposition>`.
- `health()` uses **`GET /v1/models` as the decider**. `GET /healthz` is informational only and is recorded in `detail`.
  - 401 or 403 → `unauthorized`
  - 200 with ≥1 `meterless/*` id → `online`
  - anything else, including connection refused and a 200 with no meterless ids → `offline`
- `autodetect() -> str | None` (module function): probes ports `8088, 8090, 8787, 11434` on hosts `127.0.0.1, localhost, [::1]` (port-major order, 1.5 s per probe, probe function injectable for tests). It returns the first base URL whose state is `online` or `unauthorized`. It persists the base URL only (never the token) in memory for the process.
- Retries: 1 retry on connection reset or 502/503. No retry on timeout, and no retry on 401/403, which raises `ProviderUnauthorized` ("wrong token ⇒ unauthorized, not offline").
- **Nemotron (A3):** in live mode the runtime routes `MODEL_ID` to Nemotron via Nightshift. The returned `model` field of each response is written to the trace, so the judge can see what served the call.

### 7.4 `SampleProvider`
Deterministic, no network, no randomness. `chat()` expects the last user message to be `TASK:<name>\n<json payload>` and delegates to `agent/rules.py`:

| TASK | Behaviour |
|---|---|
| `parse_question` | regex rules: metric (`revenue\|sales` → `net_revenue`; `ticket\|support` → `ticket_count`), region (`EU\|Europe`, `UK`, `US`, else `ALL`), `week\s*(\d{1,2})`, optional year, direction word (`drop\|fell\|down` / `rise\|spike\|up` / else `change`) |
| `plan` | builds sub-questions per source from the parsed question; promotes shipments to priority 1 if recalled memory mentions a carrier; adds a `memory` sub-question when memory was recalled |
| `narrate` | renders the answer text from the accepted claims and drivers (templates branch on which claims exist: driver found / no significant change / demand drop / ruled-out only) |

Its output is a pure function of its payload, and the payload is derived from the data. Nothing about NordExpress is hardcoded anywhere: the carrier name only appears because the Investigator found it in the rows.

### 8.2 `HMemStub(path)` — fully functional offline
- Persistent JSON file `{"version":1,"records":[MemoryRecord…]}`, written atomically (temp file + `os.replace`). Single writer per process, with a `threading.Lock` for the HTTP server. The directory is created on demand.
- `store`: if a `confirmed` record with the same `(entity, fact_key)` and the same `fact` exists, then `confirmations += 1` and `last_confirmed_at` is updated. If the `fact` differs, the old record becomes `superseded` (`superseded_by`, `supersede_reason="newer confirmed finding in run <id>"`) and a new record is created. Otherwise a new record is created.
- `recall`: exact match on `entity` for each requested entity; if `query` is given, additionally a case-insensitive token overlap on `fact`. Results are de-duplicated by `memory_id` and sorted by `last_confirmed_at` descending.
- **Not claimed to pass the Meterless H-MEM conformance suite.** That suite (`HMEM_IMPL=/abs/path/to/index.ts npx tsx conformance/runner.ts`) targets a TypeScript implementation. The stub's own tests are in §14.

### 8.3 `HMemMeterless` — placeholder (A2)
Same interface. The constructor and every method raise `NotConfigured("Meterless H-MEM is not wired: set ENGINE=stub, or implement HMemMeterless against engines/hmem once the engine repo is available")`. When wiring it, the TypeScript reference and its `AGENTS.md` are the source of truth, and the conformance suite above is the done-criterion for that implementation.

### 8.4 How the agent uses memory
- **Recall (Planner, start of run):** `recall(entities=parsed.entities)`. Each record is traced as an `engine_call`. Recalled records change the plan, because shipments for the recalled carrier are prioritised, and are surfaced in the answer under "Prior knowledge (H-MEM)". Recalled memory is a **hypothesis, not evidence**: it cannot support a `driver` claim by itself (Critic rule C7).
- **Store (end of run, after Critic):** for each accepted claim of kind `driver` or `delta` with `confidence ≥ 0.7`, store one record **per entity** in `claim.entities`. A NordExpress driver claim stores under `carrier:NordExpress`, `region:EU` and `week:2026-W41`.
- Entity vocabulary: `region:<R>`, `carrier:<name>`, `week:<YYYY>-W<ww>`, `category:<c>`, `metric:<m>`.

## 9. Agents

All agents receive a shared `RunContext(config, run_id, source, provider, engine, trace, deadline, counters)`. Each agent step emits trace records (§11).

```python
class Planner:
    def run(self, ctx: RunContext, question: str) -> Plan: ...
        # 1 parse (provider TASK:parse_question; validate; fallback to rules.parse_question)
        # 2 recall memory (engine.recall)
        # 3 plan (provider TASK:plan; validate JSON schema; fallback rules.plan)
        # 4 emit delegate_task → Investigator

class Investigator:
    def run(self, ctx: RunContext, plan: Plan) -> tuple[list[Evidence], list[Claim]]: ...
    def refine(self, ctx: RunContext, plan: Plan, evidence: list[Evidence],
               rejections: list[Rejection]) -> tuple[list[Evidence], list[Claim]]: ...

class Critic:
    def review(self, ctx: RunContext, claims: list[Claim], evidence: list[Evidence]) -> Review: ...
    def review_narrative(self, ctx: RunContext, text: str, accepted: list[Claim],
                         evidence: list[Evidence]) -> list[Rejection]: ...

class Explainer:
    def run(self, ctx: RunContext, plan: Plan, review: Review, evidence: list[Evidence],
            unverified: list[Rejection], recalled: list[MemoryRecord]) -> "Answer": ...
```

### 9.1 Investigator algorithm (deterministic, runs in both modes)

Let *w* be the target week and the baseline be weeks *w−4..w−1* (prior-week = *w−1*). The primary comparison is week-over-week (WoW); the 4-week mean is secondary. Thresholds: `SIGNIFICANT_DROP = 5%` on both comparisons; `DOMINANCE = 0.40` share of the delta.

| Step | Action (QuerySpec on…) | Produces |
|---|---|---|
| I1 | weekly net revenue, gross order value, order count, cancelled value for region over w−4..w (orders) | `delta` claim (WoW %, vs-4wk-mean %); decides `significant` |
| I2 | If not significant (|Δ| < threshold on either): emit `observation` claim "no significant change", **skip I3–I7**, run only the decoy-style demand check, and return | the answer to a false-premise question |
| I3 | decompose Δ(w vs w−1) by `country`, `category`, `carrier`, `status` (orders) | per-segment delta and share |
| I4 | gross vs cancelled split: is the drop in gross (demand) or in cancelled value (fulfilment)? | `ruled_out` claim for demand if gross is within ±8% |
| I5 | cancelled orders in w for region with `order_id, carrier, order_value_eur, cancel_reason` (orders, limit 5000), grouped by `carrier, cancel_reason` | candidate driver segment (carrier × reason) |
| I6 | shipments in w−1..w for region: avg `delay_days`, late share by carrier (shipments), then **in-app join** with I5 on `order_id` | corroboration: late share of the candidate carrier vs its baseline |
| I7 | tickets by category for region, w vs baseline mean (tickets), then **in-app join** to I5 on `order_id` | ticket spike ratio, share of spike tied to the candidate carrier's orders |
| I8 | build claims; rank hypotheses by `explained_share` = (segment cancelled-value increase) ÷ |Δ| | `driver` claim(s) with `evidence_ids` from orders, shipments **and** tickets; `ruled_out` claims for segments below threshold (e.g. decoy `home` category) |

For `ticket_count` questions the same flow applies with tickets as the primary metric. It decomposes by `category`, then links the dominant category to carriers via the order join and to cancellations/delays in orders and shipments.

Evidence construction: for every query the Investigator stores `Evidence` with `query`, `query_text`, named `values` (e.g. `eu_net_revenue_w41`, `wow_pct`), up to 50 `rows`, and up to 20 `row_refs` (primary keys fetched by a companion `select` query). Evidence ids are sequential `E1…`.

Confidence for a `driver` claim: `0.4*min(1, explained_share) + 0.3*(distinct_sources/3) + 0.3*(1 if Critic accepted on first pass else 0.5)`, rounded to 2 dp. This is computed in code.

`refine()` reads each `Rejection.needs` and tries to satisfy it (for example, running the missing shipments query for a `DRIVER_SINGLE_SOURCE` rejection, or re-running a query for `RECOMPUTE_FAILED`). It returns new or replacement evidence and claims.

### 9.2 Critic rules (applied to every claim)

| Code | Rule |
|---|---|
| C1 `NO_CITATION` | `evidence_ids` is empty (except `memory` kind, see C7) |
| C2 `UNKNOWN_EVIDENCE` | any `evidence_id` is not in the evidence set |
| C3 `NUMBER_MISMATCH` | any `NumberRef`'s value differs from `Evidence.values[name]` (relative tolerance 0.5% or absolute 0.01), or the name is missing |
| C4 `UNGROUNDED_NUMBER` | a numeric token in `claim.text` (ignoring `[E#]`, week labels like `week 41`/`W41`, and years) has no `NumberRef` whose formatted value (`fmt`) equals the token |
| C5 `RECOMPUTE_FAILED` | the Critic **re-executes `Evidence.query` through the DataSource** and the recomputed `values` differ (tolerance as C3). In live mode this is a second Zetaris call, traced as such. |
| C6 `ROWREF_MISSING` | a cited `row_ref` is not present in the source. Checked by `in` queries on primary keys, sampled up to 5 per evidence item. |
| C6b `DRIVER_SINGLE_SOURCE` | a `driver` claim has evidence from fewer than 2 distinct sources |
| C7 `MEMORY_NOT_FOUND` | a `memory` claim has no `memory_id`, or `engine.get(memory_id)` returns nothing. Accepted memory claims are rendered as prior knowledge only, never as findings, and never stored again. |

`review()` returns accepted and rejected claims. A `driver` or `delta` claim with any rejection is rejected whole. `review_narrative()` checks that every numeric token and every `[E#]` marker in the narrative maps to an accepted claim and an existing evidence item. On failure, the Explainer re-renders deterministically.

### 9.3 Refinement loop and limits
```
claims = Investigator.run
for attempt in 0..MAX_REFINEMENTS:        # default 2
    review = Critic.review(claims)
    if no rejections: break
    if attempt == MAX_REFINEMENTS: break
    evidence, claims = Investigator.refine(rejections)   # trace: request_refinement / refine, retry_count = attempt+1
unverified = remaining rejections   # reported in output.unverified, NEVER in the answer text
```
Global caps: `MAX_STEPS` (agent steps), `MAX_MODEL_CALLS`, `RUN_TIMEOUT_S`. On cap, return `status:"partial"` if a review exists (answer built from the accepted claims only, with a warning), otherwise a structured error (`IterationLimit` / `RunTimeout`).

### 9.4 Explainer
Builds an `Answer`:
```python
@dataclass
class Answer:
    headline: str
    drivers: list[dict]      # {rank, claim_id, text, explained_share, confidence, evidence_ids}
    ruled_out: list[dict]
    prior_knowledge: list[dict]   # recalled memory, labelled, each with memory_id
    caveats: list[str]       # always lists unverified count; data_as_of; synthetic-data notice in sample mode
    text: str                # full narrative, [E#] markers
```
The narrative comes from the `TASK:narrate` provider call, then `Critic.review_narrative`. Fallback to `rules.render_answer`. When nothing is significant, the headline says so (no invented cause).

## 10. Orchestrator (`agent/orchestrator.py`)

```python
def run_question(question: str, *, run_id: str | None = None, options: dict | None = None,
                 config: Config | None = None) -> dict:   # returns the success OR error JSON (§12); never raises
```
Flow: `start_run` → build components (sample or live; engine selection) → Planner → Investigator → refinement loop with Critic → store confirmed findings in H-MEM → Explainer (+ narrative check) → `complete_run`. All `WhyAgentError`s and unexpected exceptions are converted to the error contract (§13); unexpected ones become `InternalError` (recoverable false) and the trace gets a final `error` record. The trace file is always closed and flushed.

`run_id` default: `run-<UTC yyyymmddHHMMSS>-<4 hex>`. The sanitised pattern is `[A-Za-z0-9._-]{1,64}`; anything else → `InvalidRequest`.

**Fallback option:** `options.fallback_to_sample` (default `false`). If a live source or provider is unavailable and this is `true`, the run continues with CsvSource/SampleProvider, and the output has `degraded:true` plus a warning (and a `fallback` trace record). If `false`, a structured error is returned.

## 11. Trace and logging (`agent/trace.py`)

File: `logs/trace-<run_id>.jsonl`, one JSON object per line, UTF-8, opened in append mode, flushed per line. `trace_id = "trace-<run_id>"`.

### 11.1 Record schema

Required fields (from the technical guide) are in every line:

| field | type | notes |
|---|---|---|
| `timestamp` | str | UTC, `YYYY-MM-DDTHH:MM:SSZ` |
| `run_id` | str | |
| `agent_name` | str | `Planner` \| `Investigator` \| `Critic` \| `Explainer` \| `Orchestrator` |
| `action` | str | vocabulary below |
| `input_summary` | str | ≤300 chars, redacted |
| `output_summary` | str | ≤300 chars, redacted |
| `target_agent` | str \| null | the next agent, or `source:<name>`, `provider:<name>`, `engine:<name>` for service calls |
| `confidence` | float \| null | 0–1 where meaningful, else null |
| `retry_count` | int | refinement-loop or retry number, 0 default |
| `status` | str | `success` \| `error` \| `rejected` \| `retry` \| `fallback` \| `skipped` |

Additional fields: `step` (int, monotonic from 1), `kind` (`agent_step` \| `source_call` \| `provider_call` \| `engine_call`), `duration_ms` (int), `details` (object, redacted).

`details` per kind:
- `source_call`: `source`, `table`, `query_text`, `row_count`, `http_status` (live).
- `provider_call`: `provider`, `model` (as returned), `task`, `http_status`, `usage`.
- `engine_call`: `engine`, `op` (`recall` \| `store` \| `get`), `entity`, `memory_ids`.

Action vocabulary: `start_run, parse_question, recall_memory, delegate_task, source_query, provider_call, compute_delta, propose_claims, review_claims, accept_claim, reject_claim, request_refinement, refine, store_memory, synthesize_answer, fallback, complete_run, error`.

### 11.2 stdout
One line per record: `[INFO] run_id=<id> <agent_name> <action>: <output_summary>`. Rejections and fallbacks log at `WARNING`, errors at `ERROR`. The last line is `[INFO] run_id=<id> Completed in <s> seconds`. With `--json`, log lines go to **stderr** so stdout is pure JSON. The trace file is identical either way.

### 11.3 Redaction (`Redactor`)
Applied to every string before it is written. It replaces (a) the exact values of `METERLESS_API_KEY`, `MODEL_API_KEY`, `ZETARIS_API_KEY`, `NVIDIA_API_KEY` and any `k=` value parsed from a connect link with `***redacted***`; (b) regex `Bearer\s+\S+`; (c) `#k=[^\s&]+`; (d) `sk-[A-Za-z0-9_-]{6,}`. Prompts and responses are summarised, never dumped.

### 12.1 CLI

|---|---|
| `POST /run` | body ≤64 KB JSON; returns the §12.3 body |

## 13. Error contract (`agent/errors.py`)

```json
{ "run_id": "demo-001", "status": "error",
  "error": { "type": "ProviderUnauthorized", "message": "Meterless Runtime rejected the token (HTTP 401).",
             "recoverable": true, "details": {"http_status": 401} },
  "trace_id": "trace-demo-001", "log_file": "logs/trace-demo-001.jsonl", "execution_time_seconds": 1.2 }
```

| `type` | recoverable | When |
|---|---|---|
| `InvalidRequest` | true | bad JSON, empty query, bad `run_id`, body too large |
| `QuestionNotSupported` | true | no metric or week can be parsed from the question |
| `ConfigError` | true | missing/placeholder credentials in live mode, bad env values |
| `ProviderUnauthorized` | true | 401/403 from `/v1/models` or chat, or the `rt-local` placeholder token |
| `ProviderUnavailable` | true | provider offline / refused / no `meterless/*` models |
| `SourceUnauthorized` | true | Zetaris 401/403 |
| `SourceUnavailable` | true | Zetaris unreachable after retries |
| `SourceQueryError` | false | invalid QuerySpec / Zetaris 4xx other than auth |
| `UpstreamTimeout` | true | timeout after retries |
| `EngineNotConfigured` | true | `ENGINE=meterless` while `HMemMeterless` is the placeholder |
| `NoData` | true | the target week has no rows for the region |
| `IterationLimit` | true | `MAX_STEPS` / `MAX_MODEL_CALLS` hit before any review |
| `RunTimeout` | true | `RUN_TIMEOUT_S` exceeded before any review |
| `InternalError` | false | any unexpected exception |

Rules: messages are redacted, with no stack traces and no secrets. The exception class name goes into the trace `details` only. The trace file always receives a terminal `error` record. With `fallback_to_sample=true`, the source/provider errors above trigger the fallback instead (`degraded:true`).

## 15. Samples (`samples/`)

`samples/questions.json`:
```json
[
  {"id": "sample-01", "question": "Why did EU revenue drop in week 41?"},
  {"id": "sample-02", "question": "Why did EU support tickets spike in week 41?"},
  {"id": "sample-03", "question": "Why did US revenue drop in week 41?"}
]
```
- 01 is the main case: a cited carrier-delay explanation, with demand ruled out.
- 02 is run **after** 01 against the same memory file and shows H-MEM recall.
- 03 is a negative control, a false premise: it reports "no significant change" and names no driver.

`scripts/run_samples.py` deletes `.hmem/samples.json`, then runs the three questions in order via `python run.py "<q>" --run-id <id> --json --out samples/outputs/<id>.json` with `SAMPLE_MODE=true HMEM_PATH=.hmem/samples.json`, and copies each trace to `samples/outputs/<id>.trace.jsonl`. **Outputs are only ever produced by this script. They are never hand-written or edited.** README tells readers to regenerate with it.

## 16. Docker

```dockerfile
FROM python:3.12-slim
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PORT=8000 SAMPLE_MODE=true
COPY requirements.txt .
RUN pip install --no-cache-dir --upgrade pip && pip install --no-cache-dir -r requirements.txt
RUN useradd --create-home --uid 10001 appuser
COPY . .
RUN mkdir -p /app/logs /app/.hmem && chown -R appuser:appuser /app
USER appuser
EXPOSE 8000
CMD ["python", "run.py", "--serve"]
```
Secrets are passed at runtime (`docker run --rm -p 8000:8000 --env-file .env why-agent`), never at build time. Nothing installs during a run. No GPU is needed. `SAMPLE_MODE=true` as the image default means a judge's first `curl` works offline. For live mode, override with `-e SAMPLE_MODE=false` plus the credentials.

Smoke test:
```
curl -s localhost:8000/run -H 'content-type: application/json' \
  -d '{"input":{"query":"Why did EU revenue drop in week 41?"}}'
```
